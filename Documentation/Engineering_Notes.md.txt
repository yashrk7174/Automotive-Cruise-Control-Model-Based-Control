# Engineering Notes

## Project 01: Automotive Cruise Control System

## Professional Version 2

# 1. Project Objective

The objective of this project is to develop a professional MATLAB and Simulink based automotive cruise-control system.

The project demonstrates a complete control-engineering workflow:

* Mathematical modelling
* Controller design
* MATLAB implementation
* Simulink implementation
* Sensitivity analysis
* Performance evaluation
* MATLAB-Simulink cross-validation
* Actuator-aware control design
* Engineering decision making
* Technical documentation

The project progresses from classical feedback control to modern state-feedback control.

Controller development is performed in four stages:

1. P Controller
2. PI Controller
3. PID Controller
4. LQR Controller

---

# 2. System Description

The system represents a simplified longitudinal vehicle model.

The vehicle dynamics are:

m dv/dt + b v = u

where:

* m = vehicle mass
* b = aerodynamic and rolling resistance coefficient
* v = vehicle velocity
* u = applied control force

The corresponding transfer function is:

G(s) = 1 / (m s + b)

# PHASE 01 — P CONTROLLER

# 5. P Controller Design

The first controller was implemented as a proportional controller:

C(s) = Kp

The objective of the P-controller stage was to establish a classical-control baseline before introducing integral and derivative action.

The proportional controller produces:

u(t) = Kp e(t)

where e(t) is the tracking error.

---

# 6. Simulink Implementation

The Simulink implementation contains:

* Reference input
* Error calculation
* P controller
* Vehicle plant
* Feedback loop
* Output logging

The Simulink model was designed to represent the same mathematical structure as the MATLAB implementation.

This allowed the analytical MATLAB model and numerical Simulink implementation to be independently compared.

# ENGINEERING DECISION — P CONTROLLER

Decision:

Kp = 500 was selected as the P-controller baseline.

Evidence:

Kp = 500 provides:

* Rise time = 3.99 s
* Settling time = 7.11 s
* Zero overshoot
* Stable closed-loop pole
* Acceptable response speed for a baseline controller

Higher gains provide faster response but increase actuator demand.

The P-controller also retains approximately 9.09% steady-state error.

Why:

Kp = 500 provides a reasonable baseline between transient performance, tracking accuracy and control effort.

Rejected alternatives:

* Kp = 50, 100 and 200 were too slow.
* Kp = 1000 and 2000 were faster but required more aggressive control action.

Consequence:

Kp = 500 was frozen as the proportional-gain baseline and carried forward into PI controller development.

Next engineering action:

Introduce integral action to reduce the remaining steady-state error.

# PHASE 02 — PI CONTROLLER

# 11. PI Controller Design

The P controller was extended with integral action.

The PI controller is:

C(s) = Kp + Ki/s

The proportional gain was intentionally kept fixed:

Kp = 500

Only Ki was varied.

This preserves the Phase 01 decision and isolates the effect of integral action.

---

# 13. PI Controller Selection

The selected PI controller is:

Kp = 500

Ki = 20

The corresponding controller is:

C(s) = 500 + 20/s

Ki = 5 and Ki = 10 resulted in excessively long settling times.

Ki = 40 reduced the steady-state error further but introduced 3.05% overshoot and increased settling time.

Ki = 80 introduced approximately 9.47% overshoot and produced a complex-conjugate pole pair, indicating reduced damping.

Therefore Ki = 20 provided the best engineering compromise.

---

# 14. Final PI Closed-Loop Model

For:

G(s) = 1 / (1000s + 50)

and:

C(s) = 500 + 20/s

the closed-loop system is:

Gcl(s) = (500s + 20) / (1000s^2 + 550s + 20)

Closed-loop poles:

s1 = -0.5108

s2 = -0.0392

Both poles are located in the left half plane.

Therefore the PI closed-loop system is stable.

# PHASE 03 — PID CONTROLLER

# 18. PID Controller Objective

The objective of Phase 03 was to extend the validated PI controller to a practical PID controller.

The PID stage investigated:

* Derivative action
* Kd sensitivity
* Combined gain selection
* Control effort
* Derivative filtering
* Filter sensitivity
* MATLAB implementation
* Simulink implementation
* MATLAB-Simulink cross-validation

The objective was not to obtain the fastest theoretical response, but to obtain a technically reasonable controller considering tracking, transient behaviour and actuator demand.

---

# 19. PID Controller Structure

The ideal PID controller is:

C(s) = Kp + Ki/s + Kd s

The ideal derivative was first studied to understand its theoretical effect.

For practical implementation, the derivative term was replaced by a filtered derivative:

C(s) = Kp + Ki/s + Kd Ns/(s + N)

where:

* Kp = proportional gain
* Ki = integral gain
* Kd = derivative gain
* N = derivative filter coefficient

---

# 20. Derivative-Gain Sensitivity

The derivative-gain sensitivity study used:

Kp = 500

Ki = 20

Kd = [0, 5, 10, 20, 40, 80]

The results showed that increasing Kd did not provide a significant improvement for this first-order vehicle plant.

Observed behaviour:

* Rise time increased slightly.
* Settling time increased slightly.
* Overshoot remained approximately zero.
* Steady-state error remained very small.
* Calculated control effort decreased.

This demonstrated that derivative action does not automatically improve every plant.

Its usefulness depends on the plant dynamics and performance objective.

---

# 21. Ideal Derivative Limitation

The ideal derivative term:

Kd s

produces an improper transfer function when Kd > 0.

Therefore the ideal mathematical derivative is not directly realizable as a causal physical controller.

The derivative term is also sensitive to high-frequency measurement noise.

For practical implementation, a filtered derivative was therefore introduced.

---

# 22. PID Gain Feasibility Study

A systematic gain search was performed using:

Kp = [400, 500, 600]

Ki = [10, 20, 30]

Kd = [0, 10, 20]

A total of 27 gain combinations were evaluated.

Project-level requirements were defined as:

* Closed-loop stability
* Settling Time < 10 s
* Overshoot <= 5%
* Steady-State Error < 0.005

Ten controller combinations satisfied all defined requirements.

The study demonstrated that stability alone is insufficient for controller selection.

---

# 23. Selected PID Gains

The selected PID gains were:

Kp = 500

Ki = 30

Kd = 20

with derivative filter:

N = 10

The controller was selected based on combined performance rather than minimizing one individual metric.

# PHASE 04 — LQR CONTROLLER

# 28. Motivation for LQR

LQR was introduced to demonstrate the transition from classical feedback control to modern state-space control.

Unlike P, PI and PID controllers, LQR directly uses a state-space representation and optimizes a cost function involving:

* State deviation
* Control effort

The LQR controller is:

u = -Kx

The objective is to obtain a stable and effective controller while explicitly considering control effort.

---

# 29. Actuator-Aware State-Space Model

For the LQR stage, the original first-order vehicle model was extended to include actuator dynamics.

Vehicle dynamics:

m dv/dt + b v = F

Actuator dynamics:

tau_a dF/dt + F = u

Parameters:

* m = 1000 kg
* b = 50 Ns/m
* tau_a = 0.5 s

The state vector is:

x = [v, F]

where:

* v = vehicle speed
* F = actuator force

The resulting state-space model is:

A =
[-0.05   0.001
0     -2]

B =
[0
2]

C =
[1  0]

D = 0

The open-loop poles are:

-0.05 and -2

---

# 30. Controllability Verification

Before LQR design, controllability was explicitly verified.

The controllability matrix was calculated and its rank was:

rank(C) = 2

for a two-state system.

Therefore:

Controllability = PASS

Both states of the actuator-aware model can be influenced through the control input.

The model is therefore suitable for state-feedback LQR design.

State estimation was not included because estimation is outside the scope of Project 01 and will be addressed in the subsequent estimation-focused project.

---

# 31. LQR Baseline Design

The LQR cost function is:

J = integral(x'Qx + u'Ru) dt

The controller was designed using the actuator-aware state-space model.

The baseline configuration used:

Q = [1 0
0 0]

R = 2.0408e-06

The resulting feedback gain was approximately:

K = [637.7980  0.2798]

Closed-loop poles:

-0.7581
-1.8514

The system was stable and achieved accurate tracking with reference scaling.

However, the unconstrained LQR control demand was slightly above the actuator limit.

This demonstrated that ideal closed-loop performance alone was insufficient for final controller selection.

---

A structured relative Q/R sensitivity study was performed.

The objective was to understand the trade-off between:

* Tracking performance
* Response speed
* Control effort
* Actuator feasibility

Results:

| Low State Priority     |          0.5 |   4.5196 |       8.2026 |             0 | approximately 0 |    497.5 | Yes      |
| Baseline               |          1.0 |   3.2658 |       5.8542 |             0 | approximately 0 |    701.8 | No       |

# 33. Actuator Constraint

The specified actuator force limit is:

Maximum Actuator Force = 700 N

The baseline LQR produced:

Raw control peak = 701.786 N

Therefore the unconstrained baseline slightly exceeded the actuator capability.

The difference was:

701.786 N - 700 N = 1.786 N

This is a small violation, but it cannot be ignored in an engineering design.

The actuator limit was therefore treated as a hard constraint.

# ENGINEERING DECISION — LQR CONTROLLER

Decision:

Retain the baseline LQR controller as the final LQR configuration and explicitly include actuator saturation in the final validation.

Evidence:

The LQR sensitivity study demonstrated a direct trade-off between response speed and actuator demand.

The baseline configuration provides:

* Rise time ≈ 3.26 s
* Settling time ≈ 5.85 s
* Zero overshoot
* Zero steady-state error
* Stable closed-loop poles

The unconstrained peak command is:

701.786 N

while the actuator capability is:

700 N

The final saturated implementation produces:

* Actual peak = 700 N
* Saturation duration = 0.0042% of samples
* Stable closed-loop response
* Zero steady-state error

Why:

The actuator constraint is a physical limitation and must therefore be considered part of the controller validation rather than ignored.

The small saturation event does not prevent the system from achieving the required tracking objective.

Rejected approach:

The unconstrained LQR result cannot be considered the final physical implementation because it exceeds the actuator limit.

Consequence:

The actuator-aware, saturation-validated LQR controller is accepted as the final modern-control benchmark for Project 01.

# 35. Overall Controller Comparison

The project progressed through four controller architectures.

| Controller | Main Advantage                                                    | Main Limitation                                      |
| ---------- | ----------------------------------------------------------------- | ---------------------------------------------------- |
| P          | Simple and transparent                                            | Steady-state error                                   |
| PI         | Eliminates steady-state tracking error                            | Slower transient response                            |
| PID        | Improved transient response with practical derivative action      | More tuning parameters and actuator sensitivity      |
| LQR        | State-feedback optimisation and explicit control-effort trade-off | Requires state-space model and actuator-aware design |

The controllers were not evaluated only by their fastest response.

The selection process considered:

1. Stability
2. Tracking accuracy
3. Rise time
4. Settling time
5. Overshoot
6. Control effort
7. Actuator constraints
8. Implementation realism
9. MATLAB-Simulink consistency

# 36. Engineering Lessons

The project established several control-engineering principles.

## 36.1 Gain Increase Is Not Always Better

Increasing controller gains can improve transient response but can also increase control effort and reduce practical feasibility.

---

## 36.2 Integral Action Addresses Steady-State Error

The P-controller could not eliminate the steady-state tracking error.

Integral action significantly reduced this error.

---

## 36.3 Derivative Action Is Plant Dependent

Derivative action did not provide a major benefit for the simplified first-order cruise-control plant.

Therefore derivative action should not be added solely because a PID controller has three terms.

---

## 36.4 Practical Controllers Must Consider Realisation

The ideal derivative is mathematically useful but not directly realizable.

A filtered derivative is more appropriate for practical implementation.

---

## 36.5 Control Effort Must Be Evaluated

A controller that produces excellent tracking but requires unrealistic actuator effort is not automatically a good engineering solution.

---

## 36.6 Actuator Constraints Are Design Constraints

The LQR study demonstrated that actuator capability must be treated as a hard engineering constraint.

The raw LQR command and actual saturated actuator output were therefore evaluated separately.

---

## 36.7 Validation Must Be Independent

MATLAB and Simulink were treated as separate implementations.

Cross-validation was used to confirm that both implementations represent the same intended control system.
